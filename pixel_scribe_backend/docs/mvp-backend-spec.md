# Spec: Pixel Scribe Backend MVP

## Status

Approved on 2026-08-08. Implementation remains gated on approval of the follow-up
task plan.

## Objective

Build a Gleam backend for virtual-office rooms. A visitor chooses a display
username in the frontend, enters an office room, sees who is connected there, and
exchanges real-time text messages with that room.

The MVP is successful when a typical group of fewer than 20 people, and at most
50 concurrent people, can use the built-in `default` room through one backend
process without accounts or durable storage. The public protocol identifies rooms
explicitly so later releases can accept more room IDs without changing event
shapes.

## Product Scope

### Included

- One active office room identified as `default`.
- A room-aware WebSocket contract in which every room-scoped event identifies its
  room.
- Non-unique display usernames chosen before connecting.
- A distinct, server-issued ID for every joined WebSocket connection.
- Current-user presence with join and leave notifications.
- Real-time plain-text chat.
- The latest 50 accepted messages, stored in memory and sent to new arrivals.
- A Wisp HTTP server that serves the compiled frontend and WebSocket endpoint.
- A single BEAM application instance.

### Excluded

- Authentication, accounts, permissions, and durable user sessions.
- SQLite, chat persistence, schemas, and migrations.
- Runtime support for rooms other than `default`.
- Avatar coordinates, movement, and server-side slot assignment.
- Delivery acknowledgements, retries, and offline delivery.
- Multiple backend replicas or BEAM-node coordination.
- Voice, video, and screen sharing.

## User and Connection Lifecycle

1. The frontend reads and writes the username preference in a browser cookie.
   The backend does not own or trust that cookie.
2. After the user chooses a label and office, the frontend opens the WebSocket and
   sends one `join_room` event with a room ID. The MVP frontend always sends
   `default`.
3. The backend validates the room ID and label, confirms that the room exists,
   enforces its capacity, assigns an opaque connection ID, and records the
   presence.
4. The joining client receives a room snapshot containing the room ID, its own ID,
   all current presences in that room, and up to 50 recent room messages.
5. Other clients joined to that room receive a `user_joined` event.
6. The username and joined room cannot change during the connection. Switching
   rooms later requires a new connection.
7. On disconnect, the backend removes only that connection ID and broadcasts a
   `user_left` event to that room exactly once.
8. Reconnecting creates a new presence and connection ID. Reusing the cookie's
   username makes this appear continuous to the user, but it is not session
   restoration.

Two connections in a room may use the same username. One connection can never
replace, rename, disconnect, or otherwise control another connection by copying
its label.

## Domain Model

### Room identity

- `roomId`: an opaque public string carried as `room_id` in JSON.
- The only room ID accepted by the MVP is `default`.
- Valid room IDs contain 1–64 lowercase ASCII letters, digits, underscores, or
  hyphens and begin with a letter or digit.
- A WebSocket connection can join exactly one room.

Clients must treat room IDs as opaque identifiers rather than deriving display
names, permissions, or URLs from them. Supporting multiple offices later expands
the set of accepted IDs; it does not require a new event shape.

### Presence

- `connectionId`: opaque string generated by the server and unique for the life of
  the server process.
- `username`: validated display label within the joined room.

Coordinates are deliberately absent. Future position data must be introduced as
additive protocol fields or events.

### Chat message

- `messageId`: opaque string generated by the server and unique for the life of
  the server process.
- `senderId`: the sender's connection ID.
- `username`: the sender's display label at send time.
- `text`: validated plain Unicode text.
- `sentAt`: server-generated UTC timestamp encoded as RFC 3339.

Each room serializes its accepted messages, stores its newest 50, and broadcasts
each one once to all connections joined to that room, including the sender. The
WebSocket stream is best effort; clients do not acknowledge messages. A
reconnecting client uses message IDs to deduplicate any messages also present in
its new room snapshot.

## Validation Rules

All WebSocket input is untrusted and is decoded and validated at the connection
boundary.

Required username rules:

- Trim leading and trailing whitespace.
- Require 1–32 Unicode grapheme clusters after trimming.
- Allow duplicate names, spaces, and emoji.
- Reject control characters and line breaks.

Room ID rules:

- Require a string matching `[a-z0-9][a-z0-9_-]{0,63}`.
- Reject an invalid shape with `invalid_room_id`.
- Reject a valid but unsupported ID with `room_not_found`.
- Accept only `default` in the MVP.

Message rules:

- Accept text messages only; never interpret text as HTML or markup.
- Trim leading and trailing whitespace.
- Require 1–500 Unicode characters after trimming.
- Reject oversized, malformed, binary, or unknown events.
- Limit each decoded WebSocket event to 8 KiB in addition to the character limit.

The frontend must render usernames and messages as text, not HTML.

## Security and Abuse Model

The trust boundaries are the HTTP request, WebSocket upgrade, and every incoming
WebSocket event. The assets being protected are room availability, process memory,
and the integrity of presence and chat state. The server stores no credentials or
sensitive profile data in the MVP.

There is deliberately no application access control. Anyone who can reach the URL
and knows a room ID can join, read that room's in-memory history, copy a display
label, send chat, or consume one of its 50 presence slots. The MVP room ID is
publicly known as `default`; it is not a secret or authorization token. Same-origin
checks prevent an unrelated webpage from silently opening a browser socket, but
they do not stop a direct client. A private office that needs restricted
membership must be placed behind an external access control such as a VPN or
authenticating reverse proxy until application auth is explicitly added.

MVP abuse controls:

- Enforce event-size and field-length limits before updating room state.
- Require a join within 10 seconds so idle unjoined sockets do not remain forever.
- Rate-limit chat independently per connection with a token bucket: allow a burst
  of 5 messages and refill 1 message per second.
- Return a recoverable `rate_limited` error when the chat limit is exceeded.
- Enforce the 50-presence limit atomically within each room process.
- Restrict production WebSocket origins and development origins by explicit
  configuration; never use a wildcard origin.
- Serve browser security headers, including a same-origin Content Security Policy,
  `X-Content-Type-Options`, and a restrictive framing policy.
- Use HTTPS/WSS at the deployment edge. Wisp may run behind a TLS-terminating
  reverse proxy.
- Do not log usernames, chat contents, cookies, or raw malformed payloads by
  default.

## HTTP Interface

- `GET /healthz`: return a small success response for process health checks.
- `GET /ws`: upgrade a valid request to the application WebSocket.
- `GET /`: serve the compiled frontend entry document.
- Static asset paths: serve files from `priv/public` without directory traversal.
- Unknown paths: return `404` rather than exposing filesystem details.

Production accepts WebSocket upgrades only from the application's own origin.
Development may allow explicitly configured frontend origins. The listening port,
static asset directory, and development origins are configuration values with
safe defaults.

## WebSocket Contract

Events are UTF-8 JSON objects with a string `type` discriminator. Event names and
fields use `snake_case`. Every room-scoped event carries `room_id` at the top
level. New optional fields and new event types may be added; existing field
meanings must not change silently.

### Client to server

```json
{"type":"join_room","room_id":"default","username":"Ada"}
```

```json
{"type":"send_message","room_id":"default","text":"Hello!"}
```

`join_room` must be the first application event and may succeed only once. A
client cannot send messages before joining. The `room_id` on later client events
must match the joined room; a mismatch is rejected without mutating either room.

The MVP accepts only `default`. Future multiple-office support adds accepted room
IDs while preserving these event shapes and the one-room-per-connection rule.

### Codec behavior

The protocol codec accepts either a WebSocket text frame or binary frame. Binary
frames are rejected as `invalid_event`, even when their bytes happen to contain
valid JSON. Text frames must contain one UTF-8 JSON object no larger than 8 KiB
(8,192 bytes is accepted; 8,193 bytes is rejected). The decoder requires the
`type` discriminator and the fields shown above, uses the documented
`snake_case` names, and ignores unknown fields so additive optional fields remain
forward-compatible.

Client decoding returns trusted `join_room` or `send_message` values only after
constructing the validated domain types. Its stable failures map as follows:

| Input failure | Codec failure | Public error code |
|---|---|---|
| Binary frame or payload larger than 8 KiB | `BinaryPayload` or `PayloadTooLarge` | `invalid_event` |
| Malformed JSON, unknown type, or missing/wrong-shaped required field | `MalformedEvent` | `invalid_event` |
| Invalid room-ID shape | `InvalidRoomIdValue` | `invalid_room_id` |
| Invalid username | `InvalidUsernameValue` | `invalid_username` |
| Invalid message text | `InvalidMessageTextValue` | `invalid_message` |

The codec does not expose `gleam_json` parser details. A connection may include a
validated room ID in an error response when it can recover one; otherwise the
error's `room_id` is `null`.

### Server to client

```json
{
  "type": "room_state",
  "room_id": "default",
  "self_id": "connection-123",
  "users": [{"connection_id": "connection-123", "username": "Ada"}],
  "messages": []
}
```

```json
{
  "type": "user_joined",
  "room_id": "default",
  "user": {"connection_id": "connection-456", "username": "Grace"}
}
```

```json
{"type":"user_left","room_id":"default","connection_id":"connection-456"}
```

```json
{
  "type": "message_sent",
  "room_id": "default",
  "message": {
    "message_id": "message-789",
    "sender_id": "connection-123",
    "username": "Ada",
    "text": "Hello!",
    "sent_at": "2026-08-08T20:15:00Z"
  }
}
```

```json
{
  "type": "error",
  "room_id": "default",
  "code": "invalid_message",
  "message": "Message must contain between 1 and 500 characters.",
  "recoverable": true
}
```

Every error event includes `room_id`, using `null` when no valid room context can
be recovered from the input. Initial error codes:

- `invalid_event`: malformed JSON, an unknown type, or an invalid event shape.
- `join_required`: a room-scoped event was sent before joining.
- `already_joined`: a second room join was attempted on the same connection.
- `invalid_room_id`: the room ID failed shape validation.
- `room_not_found`: the room ID is valid but not supported by the server.
- `room_mismatch`: an event's room ID differs from the connection's joined room.
- `room_unavailable`: the joined room process stopped and the client must reconnect.
- `invalid_username`: the display label failed validation.
- `invalid_message`: the chat text failed validation.
- `rate_limited`: the connection is sending chat faster than allowed.
- `room_full`: 50 presences are already joined to the requested room.

The encoder owns the stable public message and recoverability metadata for every
error code:

| Code | Message | Recoverable |
|---|---|---|
| `invalid_event` | `Invalid event.` | No |
| `join_required` | `Join a room before sending messages.` | Yes |
| `already_joined` | `This connection has already joined a room.` | Yes |
| `invalid_room_id` | `Room ID is invalid.` | Yes |
| `room_not_found` | `Room not found.` | Yes |
| `room_mismatch` | `Room ID does not match the joined room.` | Yes |
| `room_unavailable` | `Room is unavailable. Reconnect to continue.` | No |
| `invalid_username` | `Username must contain between 1 and 32 characters.` | Yes |
| `invalid_message` | `Message must contain between 1 and 500 characters.` | Yes |
| `rate_limited` | `You are sending messages too quickly.` | Yes |
| `room_full` | `Room is full.` | No |

Client input errors return the same structured error shape. Internal details and
stack traces are never sent to clients. The non-recoverable codes
`invalid_event`, `room_full`, and `room_unavailable` close the WebSocket after the
error is sent; recoverable validation errors leave it open. The connection phase
after each error and the exact close sequence are finalized with the connection
state machine in Task 7.

The error inventory and exact behavior may be refined while the protocol codecs
and connection state machine are implemented. Before Tasks 3 and 7 are complete,
this section must contain the implemented error behavior, including each code's
room context, recoverability, socket-close behavior, and resulting connection
phase. Codec and connection tests must lock the documented behavior. Refinement
may clarify the contract but must not silently expand the approved MVP scope.

## BEAM Process Architecture

The backend uses supervised, typed Gleam actors for shared state. Network decoding
and socket I/O stay in per-connection WebSocket processes; shared room state stays
in one room actor. No browser input becomes an Erlang process name or atom.

### Supervision tree

```text
Application static supervisor (RestForOne)
├── Room directory actor                 permanent worker
├── Room factory supervisor              permanent supervisor
│   └── Default room actor               dynamic worker created at startup
└── Mist/Wisp HTTP server supervisor     permanent supervisor
    └── WebSocket connection process     transient, one per socket
```

The children start in dependency order. `RestForOne` gives the following behavior:

- If the room directory fails, the directory, room factory with all room children,
  and web server restart. The factory creates a fresh default room before the web
  server accepts traffic.
- If the room factory fails, it and the web server restart, and the factory creates
  a fresh default room.
- If only a room actor fails, the factory restarts that room from its original
  start arguments. Connections monitoring that room close and reconnect, while
  unrelated infrastructure remains running.
- If only the web server fails, it restarts without deliberately discarding the
  room's message history. Its terminated connection processes are removed from
  room presence through connection monitors.
- Restart intensity is bounded so a crash loop eventually terminates the
  application for the deployment runtime to restart, rather than looping forever.

The application creates one fixed name for the room directory and one fixed name
for the room factory at startup, then passes them to child specifications. Room
IDs remain validated strings stored in the directory map. The application must
never create registered names dynamically from room IDs because BEAM registered
names are backed by a finite atom table.

### Process responsibilities

| Process | Owns | Does not own |
|---|---|---|
| Application supervisor | Child order, restart strategy, shutdown | Product state or WebSocket payloads |
| Room directory actor | `RoomId -> Room` lookup and room-process monitors | Presence, history, or socket I/O |
| Room factory supervisor | Starting, supervising, and restarting room actors; shutting them down with the factory | Room lookup, presence, or history |
| Default room actor | Presence map, connection monitors, message sequence, latest 50 messages | JSON decoding, cookies, or socket writes |
| HTTP server supervisor | Listener and HTTP/WebSocket infrastructure | Room state |
| WebSocket connection process | Protocol phase, joined room handle and monitor, validation, join timer, rate limiter, JSON encoding, socket I/O | Other users or shared history |

Mist creates a process for each upgraded WebSocket. Its initialization callback
creates a typed subject and selector for room-to-connection messages. That process
is the connection actor for this design; it is not wrapped in another actor.

### Actor handles

Other modules receive opaque handles rather than actor state or raw mailboxes:

```gleam
pub opaque type RoomDirectory {
  RoomDirectory(subject: Subject(RoomDirectoryMessage))
}

pub opaque type Room {
  Room(id: RoomId, subject: Subject(RoomCommand), pid: Pid)
}

pub opaque type ConnectionSink {
  ConnectionSink(subject: Subject(RoomEvent), pid: Pid)
}
```

Public wrapper functions validate arguments, apply bounded call timeouts where a
reply is required, and hide message constructors from unrelated modules.

### Room factory startup

The room factory is a named `gleam_otp` factory supervisor whose worker template
starts one room actor from typed arguments:

```gleam
pub type RoomStartArguments {
  RoomStartArguments(
    room_id: RoomId,
    directory: RoomDirectory,
  )
}
```

The factory supervisor itself has no custom application message type. Callers use
its typed `start_child` API with `RoomStartArguments`. The child template starts
the room actor, and the room actor registers its new handle with the directory
during initialization.

The factory's supervised start wrapper performs these steps before reporting that
the factory child has started successfully:

1. Start the named factory supervisor with the room child template.
2. Start a child using `RoomStartArguments(default_room_id, directory)`.
3. Wait for the default room's successful directory registration.
4. Return the started factory handle, allowing the root supervisor to start the
   HTTP server next.

If starting or registering the default room fails, the wrapper shuts down the
newly started factory and returns a startup error rather than serving traffic
without the required room. Room children use a restart policy that restarts
abnormal failures from the same arguments. The default room is not intentionally
stopped during normal MVP operation.

### Messages: room directory

The directory serializes room registration and lookup:

```gleam
pub type RoomDirectoryMessage {
  RegisterRoom(
    room_id: RoomId,
    room: Room,
    reply_to: Subject(Result(Nil, RegisterRoomError)),
  )
  ResolveRoom(
    room_id: RoomId,
    reply_to: Subject(Result(Room, ResolveRoomError)),
  )
  RoomDown(pid: Pid)
}

pub type ResolveRoomError {
  RoomNotFound
}

pub type RegisterRoomError {
  RoomAlreadyRegistered
}
```

At startup, the factory-created default room registers itself as `default` before
the HTTP server accepts traffic. The directory monitors the registered room PID.
Re-registration replaces a handle only when its old owner is no longer alive; an
active duplicate returns `RoomAlreadyRegistered`. `RoomDown` removes a mapping
only when the reported PID is still the current process for that room, so a late
notification for an old room process cannot delete its replacement. In the MVP,
`ResolveRoom` can therefore return only the current default room or
`RoomNotFound`.

### Messages: connection to room

Only the room actor mutates presence or message history:

```gleam
pub type RoomCommand {
  Join(
    username: Username,
    connection: ConnectionSink,
  )
  SendMessage(
    connection_id: ConnectionId,
    text: MessageText,
  )
  Leave(connection_id: ConnectionId)
  ConnectionDown(pid: Pid)
}
```

`Join` is asynchronous. The room atomically checks capacity, generates the
connection ID, monitors the connection process, inserts the presence, and sends a
`Joined` or `JoinRejected` event back to that connection. `SendMessage` generates
the message ID and timestamp inside the room actor so its mailbox order is the
authoritative room-event order.

`Leave` and `ConnectionDown` use the same idempotent removal path. This guarantees
that a normal close and a monitor notification cannot broadcast `user_left` twice.

### Messages: room to connection

The room sends typed values to the connection's selected subject. The connection
process is the only process that converts them to JSON and writes the socket.

```gleam
pub type RoomEvent {
  Joined(
    room_id: RoomId,
    self_id: ConnectionId,
    users: List(Presence),
    messages: List(ChatMessage),
  )
  JoinRejected(room_id: RoomId, error: RoomError)
  UserJoined(room_id: RoomId, user: Presence)
  UserLeft(room_id: RoomId, connection_id: ConnectionId)
  MessageSent(room_id: RoomId, message: ChatMessage)
}
```

Local protocol problems such as malformed JSON, invalid text, a missed join
deadline, or a mismatched `room_id` are handled in the connection process and do
not enter the room mailbox. Room-owned failures such as `room_full` return through
`RoomEvent`.

The WebSocket selector also maps connection-local control signals into the handler
loop. These are not sent by the room actor:

```gleam
pub type ConnectionControl {
  FromRoom(RoomEvent)
  JoinedRoomDown(pid: Pid)
  JoinDeadlineReached
}
```

`JoinedRoomDown` becomes the public `room_unavailable` error followed by socket
closure. `JoinDeadlineReached` closes a connection that never completed
`join_room`.

### Join message flow

```text
Browser
  │  { type: join_room, room_id: default, username: Ada }
  ▼
WebSocket connection process
  │  ResolveRoom(default, reply_to)
  ▼
Room directory actor
  │  Room(default, room_subject)
  ▼
WebSocket connection process
  ├── monitor resolved room PID
  │  Join(Ada, connection_sink)
  ▼
Default room actor
  ├── monitor connection PID
  ├── add presence and build snapshot
  ├── Joined(snapshot) ───────────────► joining connection
  └── UserJoined(presence) ──────────► other room connections
```

The connection transitions through `AwaitingJoin -> Joining -> Joined`. It does
not accept chat in either pre-join state.

### Chat message flow

```text
Browser
  │  { type: send_message, room_id: default, text: Hello }
  ▼
WebSocket connection process
  ├── validate room ID, text, phase, size, and rate limit
  └── SendMessage(connection_id, text)
          ▼
      Default room actor
        ├── generate ID and UTC timestamp
        ├── append and trim history to 50
        └── MessageSent(message) ─────► every room connection, including sender
```

Actor sends are asynchronous. The room never waits for a socket write, so one slow
or failed connection cannot block broadcasts to the others.

### Disconnect and failure cleanup

- On a normal or abnormal WebSocket shutdown, Mist calls the connection's close
  callback, which sends `Leave` when the connection had joined.
- The room also monitors every joined connection process. A `Down` notification
  invokes the same removal path if the close callback did not complete.
- Each joined connection process monitors its room actor. If that actor stops, the
  connection sends a fatal `room_unavailable` error when possible and closes so a
  reconnect resolves the factory-created replacement.
- A failed connection is isolated: it removes one presence and cannot crash the
  directory or room.
- A room crash deliberately loses that room's presence and history. The room
  factory restarts it from its original room ID and directory handle. Connections
  monitoring the old room close, and the directory replaces the stale subject
  when the restarted room registers.
- The HTTP request handler never mutates room state directly.

### Multiple-room evolution

The MVP factory starts only `default`, and no public API can create another room.
When multiple offices are implemented:

1. Load or accept the additional validated room IDs.
2. Call the existing room factory with `RoomStartArguments` for each active room.
3. Let each room register its string ID in the existing directory actor.
4. Keep the connection, room command, room event, and public WebSocket shapes.
5. Apply the 50-user capacity and 50-message history independently per room.

No per-room registered process names are introduced. The string-keyed directory
is the stable routing boundary.

This design intentionally uses an O(n) broadcast for each presence or chat event.
That is appropriate for the hard limit of 50 connections per room.

- `gleam_json` for typed JSON encoding and decoding, added as a direct dependency
  during Task 0.
- Gleam's standard test runner and formatter.
- JSON codecs expressed as typed Gleam encoders and decoders.
- No database dependency in the MVP.

Task 0 adds Wisp and `gleam_json` with `gleam add wisp gleam_json`. Task 1 then
proves and documents that the resolved Wisp adapter is compatible with the locked

### Task 1 platform baseline

The web module uses Wisp 2.2.2's `wisp/wisp_mist.handler` adapter to convert a
Wisp request handler into the Mist request/response shape. Its `supervised`
function accepts the listening port, passes that adapter through `mist.new` and
`mist.port`, and then calls `mist.supervised`, producing the supervised server
child that the root supervision tree will start in Task 6.
This follows the versioned [Wisp/Mist adapter documentation](https://wisp.hexdocs.pm/wisp/wisp_mist.html)
and the locked [Mist 6.0.3 server API](https://mist.hexdocs.pm/mist.html). The
Wisp standalone example mentions `mist.start_http`; the locked Mist API exposes
`mist.start` and `mist.supervised`, so the supervised form is the compatible
choice for this application.

The MVP does not use Wisp signing, encryption, or backend-owned cookies. The
server may therefore generate any adapter-valid key base at startup, keep it only
in memory, and replace it on restart. It must never be logged or exposed. A stable
deployment secret is deferred until a feature actually needs signed or encrypted
state.

## Code Style

Use formatted, explicit Gleam types with domain-oriented names and exhaustive
pattern matching. Decode external values once at the boundary and pass trusted
types internally.

```gleam
pub type ClientEvent {
  JoinRoom(room_id: RoomId, username: String)
  SendMessage(room_id: RoomId, text: String)
}

pub type ConnectionPhase {
  AwaitingJoin
  Joining(room_id: RoomId)
  Joined(room: Room, connection_id: ConnectionId)
}
```

Prefer small modules with one clear owner. Do not add abstractions solely for
hypothetical rooms, databases, movement, or media features.

## Testing Strategy

- Unit-test room ID, username, and message validation, including Unicode and
  boundary sizes.
- Unit-test every JSON event encoder and decoder, including malformed events.
- Unit-test room transitions: joins, duplicate labels, per-room capacity, leaves,
  message ordering, and eviction beyond 50 messages.
- Actor-test directory registration, stale-handle replacement, room resolution,
  connection monitoring, idempotent leave/down cleanup, and typed message
  ordering.
- Factory-test that startup always creates and registers `default`, an abnormal
  room failure starts a replacement, and a failed default startup fails the
  factory child.
- Integration-test the WebSocket lifecycle: join snapshot, broadcasts, errors,
  unsupported and mismatched room IDs, disconnect cleanup, and reconnect as a new
  presence.
- Supervision-test that directory and factory failures restart the dependent
  children described by the `RestForOne` policy.
- Smoke-test static frontend serving, missing assets, and `/healthz`.
- Build and run the full test suite at each implementation checkpoint.

No coverage percentage is required for the MVP. Every specified state transition
and validation boundary must have at least one focused test.

## Operational Behavior

- Log application start and stop, joins, leaves, rejected joins, and unexpected
  failures without logging message contents as a default.
- Include room ID, connection ID, and current room-user count in relevant
  structured logs.
- Detect WebSocket closure and clean up presence promptly.
- Recommended: require `join_room` within 10 seconds and use WebSocket ping/pong
  support to detect dead connections that do not close cleanly.
- On graceful shutdown, stop accepting connections and close active sockets.
- A room-process restart clears all presences and message history by design.

## Boundaries

### Always

- Validate network input before it reaches room state.
- Keep the room process authoritative and serialize state transitions through it.
- Generate identity and timestamps on the server.
- Keep protocol codecs contract-tested and run format, build, and tests.
- Keep frontend artifacts reproducible; do not hand-edit generated JavaScript.

### Ask first

- Add a dependency or database, except for the explicitly approved Task 0 addition
  of Wisp and `gleam_json`.
- Change the public WebSocket contract or validation limits.
- Add authentication, another active room, coordinates, or delivery guarantees.
- Change the 50-user capacity or 50-message history limits.

### Never

- Treat a username or cookie as identity or authorization.
- Render or encourage rendering client strings as HTML.
- Let one connection mutate another connection's presence.
- Expose internal exceptions, filesystem paths, or secrets to clients.
- Commit generated build output unless the repository explicitly adopts that policy.

## Success Criteria

- A client can join `default` once with a valid username and receives `room_id`, its
  server ID, all current room users, and no more than the latest 50 room messages.
- Every room-scoped event identifies `default`, and a valid unsupported room is
  rejected with `room_not_found` without mutating default-room state.
- A message whose room ID differs from the joined room is rejected with
  `room_mismatch`.
- Two clients with the same username remain distinct and cannot control each other.
- All joined clients observe valid join, leave, and message events in room order.
- Invalid or out-of-order events receive stable structured errors and cannot mutate
  room state or crash the application.
- The 51st simultaneous join to `default` is rejected with `room_full`.
- Message 51 evicts message 1 while preserving messages 2–51 in order.
- Disconnect and reconnect produce a leave and a new presence with a new ID.
- Restarting the room clears all presence and history.
- A restarted room replaces its old directory handle, and a delayed monitor
  notification cannot unregister the replacement.
- The factory always creates and registers `default` before the HTTP server starts.
- A connection-process crash removes only that presence; a room-process crash is
  restarted by the factory without restarting the directory or HTTP server.
- Connections attached to a failed room receive `room_unavailable` when possible,
  close, and can reconnect through the directory to the replacement room.
- Static frontend files and the WebSocket are available from the same production
  origin, and `/healthz` reports process availability.
- Format, build, unit tests, and integration tests pass.
